一、总体概览：三层评测体系

AI Agent 的评估比传统 LLM 评估复杂得多——它涉及多轮工具调用、长链路推理、环境交互和任务规划。截至 2026 年中，Agent 评测领域已经形成了“三层体系”：

层次定位代表
公共模型基准
Public Benchmarks		 标准化的学术/行业基准，用于横向比较 MMLU-Pro, GPQA-Diamond, ARC-AGI-2
Agent 行为基准
Agentic Benchmarks		 多步任务完成的真实环境测试 SWE-bench, WebArena, GAIA, OSWorld
实践者评测栈
Practitioner Stack		 团队自定义评估管线、在线监控 Braintrust, LangSmith, DeepEval, Langfuse

二、学术评测分类体系（SAP Labs, KDD'25 综述）

SAP Labs 发表的综述论文（arXiv: 2507.21504）提出了二维评估分类法，是目前最系统的学术框架。

2.1 评估目标（What to Evaluate）

A. 智能体行为（黑盒视角）

子类核心指标代表 Benchmark
任务完成Success Rate, Pass Rate, pass@kSWE-bench, WebArena, ScienceAgentBench
输出质量流畅度、逻辑连贯性、事实正确性PredictingIQ, EnDex
延迟与成本TTFT, 端到端延迟, Token成本MobileBench, WebArena

B. 智能体能力（白盒视角）

子类核心指标代表 Benchmark
工具使用调用准确率、选择准确率、参数F1ToolBench, API-Bank, BFCL, FlowBench
规划与推理Node F1, Edge F1, 进展率, 步骤成功率T-Eval, AgentBoard, ReAct 范式
记忆与上下文保持事实召回准确率、一致性分数LongEval, LoCoMo（600+轮）
多智能体协作协作效率、信息共享效果AgentSims, GAMEBENCH, BALROG

C. 可靠性

子类核心关注关键发现
一致性pass@1 vs pass^k（k次全部成功）τ-benchmark 显示当前 Agent 一致性表现不佳
鲁棒性输入扰动/环境变化下的稳定性CoSafe 揭示即使先进 Agent 也被共指攻击绕过

D. 安全性与对齐

子类代表 Benchmark
公平性CASA, R-Judge, SimuCourt
伤害 / 毒性 / 偏见Agent Security Bench, AgentDojo, AgentHarm
合规与隐私Cybench, TheAgentCompany

2.2 评估过程（How to Evaluate）

维度子类关键描述
交互模式静态/离线 vs 动态/在线离线成本低但易产生误差传播；在线能发现真实痛点
评估数据人工标注、合成数据、交互生成代表：ScienceAgentBench, TaskBench, HAL
指标计算代码规则、LLM-as-Judge、Agent-as-Judge、人在回路四种方法各有优劣，需组合使用
评估工具OpenAI Evals, DeepEval, InspectAI, Phoenix, GALILEO覆盖开源到商业
评估环境Mocked API → Web 模拟器 → 真实环境从低成本低代表性到高成本高代表性

三、主流 Agent Benchmark 详解

3.1 SWE-bench（软件工程） 核心

简介2,294 个真实 GitHub Issue，需修改代码并通过现有测试
评估方式基于执行的测试（pass/fail）
子版本SWE-bench Verified（500 个人工筛选实例）、SWE-bench Multilingual
2026年SOTAlive-SWE-agent + Claude 4.5 Opus: 79.2% (Verified)
定位代码 Agent 能力评估的事实标准

3.2 AgentBench（多领域综合） 综合

简介29 个 LLM 在 8 个环境中评估
覆盖场景操作系统、数据库、知识图谱、数字卡牌游戏、网页浏览等
特点标准化评测，覆盖 8 大场景，适合 PM 横向比较
局限缺乏成本 / 可靠性维度

3.3 GAIA（通用AI助手） 通用

简介466 个真实世界问题，需推理 + 多模态 + 工具使用
特点人机性能差距 77%，对当前 Agent 极具挑战性
定位测量通用智能体接近人类水平的程度

3.4 WebArena（Web 导航）

简介812 个任务，在自托管网站（电商、论坛、地图、CMS 等）上完成
评估方式基于状态的功能正确性
延伸版本VisualWebArena（多模态）、WebCanvas

3.5 τ-bench（企业工具-Agent-用户交互） 企业

简介多轮用户交互 + 策略合规评估
两大领域零售预订 + 航空预订
关键贡献引入 pass^k 指标，发现 do-nothing 代理通过 38% 航空任务
核心发现当前 Agent 在一致性方面表现极差

3.6 OSWorld（多模态计算机操作）

简介真实计算机环境（Ubuntu/Windows/macOS）中的开放式任务
特点要求 Agent 操作真实操作系统，最具真实性
评估基于屏幕状态的执行评估

3.7 Terminal-Bench（终端命令） 新兴

简介评估 Agent 在终端环境中的命令执行能力
特点2026 年新兴，补充 OSWorld 的 CLI 视角

四、企业级评估框架 CLEAR

由 Yehudai 等人提出的 CLEAR 框架，专门针对企业部署场景，弥补了现有 Benchmark 的重大缺陷：

五维度模型

维度核心指标关键公式 / 说明
C — Cost（成本） 成本归一化准确率 (CNA)、每次成功成本 (CPS) CNA = (Accuracy / Cost) × 100
L — Latency（延迟） SLA 合规率 (SCR) SCR = SLA内完成任务数 / 总任务数
E — Efficacy（效能） 领域特定准确率 代码：测试通过率；客服：意图分类正确率
A — Assurance（保障） 策略依从得分 (PAS) PAS = 1 − (违规数/策略关键动作数)
R — Reliability（可靠性） pass@k（连续 k 次全成功） 任务关键型应用要求 pass@8 ≥ 80%

综合评分公式：

CLEAR = w₁·Cnorm + w₂·Lnorm + w₃·E + w₄·A + w₅·R

核心发现（硬数据）

  • 准确率最优配置的成本比 Pareto 最优方案贵 4.4–10.8 倍
  • CLEAR 与生产成功相关性 𝛒 = 0.83，远超传统准确率 𝛒 = 0.41
  • 实验室到生产性能差距达 37%
  • pass@1 = 60% 的系统，pass@8 仅剩 25%
  • 85% 企业实验 GenAI，仅 10% 成功部署

六、国内视角：RACE-FACT 框架

6.1 RACE 评估框架

基于参考标准和自适应准则的动态加权评估框架，用于报告质量评估：

评估维度权重示例说明
全面性 (COMP)35%报告覆盖面和完整性
洞察力 / 深度 (DEPTH)30%分析深度和专业判断
指令遵循 (INST)15%遵循任务要求程度
可读性 (READ)20%结构和表达质量

核心流程：动态权重生成 → 基于参考标准评分 → 加权总分计算

6.2 FACT 评估框架

事实丰富性和引用可信性评估框架：

  • 引用准确性 (C.Acc.)：有效支持数 ÷ 有效陈述-URL 对数
  • 每任务平均有效引用数 (E.Cit.)：量化检索呈现的有价值可验证信息

6.3 Anthropic 最佳实践建议

  1. 尽早启动：从 20–50 个真实失败/高频场景任务开始
  2. 鲁棒评分：环境隔离、只评结果不限制路径、读轨迹验证评分器
  3. 动态迭代：淘汰 100% 通过的饱和项、让业务侧参与贡献任务
  4. 评分器组合：能用代码评分器就不用 LLM 评分器，人工评分器做校准

七、评估方法论关键要点

7.1 评分器（Evaluator / Scorer）三类组合

类型方法优点缺点
代码评分器 字符串匹配、单元测试、静态分析 快、便宜、客观、可复现 脆弱，无法处理开放任务
LLM 评分器 LLM-as-Judge、成对比较 灵活、能处理开放式任务 非确定性、偏见、成本高
人工评分器 领域专家评审、众包 黄金标准 昂贵、慢、难规模化

7.2 pass@k 三个变体

指标含义适用场景
pass@1单次尝试成功率常规 Benchmark 报告
pass@kk 次尝试中至少一次成功宽松评估，容忍随机性
pass^kk 次尝试全部成功严格评估，任务关键型应用

7.3 评估数据的质量威胁

  • 污染问题：MMLU 题目出现在 Common Crawl、HumanEval 类似 LeetCode
  • 饱和问题：MMLU / HumanEval / MBPP 已无法区分前沿模型
  • 方法论不透明：“Best-of-16 + CoT + 工具” 与 “greedy zero-shot” 不可比
  • Benchmark 有效性：8/10 主流基准存在严重有效性缺陷

八、趋势与总结

当前三大根本性缺陷

1. 成本被完全忽视

无主要基准报告成本；复杂架构以 50 倍成本 换边际准确率

2. 可靠性未被测量

单次运行成功掩盖脆弱性
（pass@1=60% → pass@8=25%）

3. 企业关键维度缺失

无安全评估、无策略合规、无延迟 SLA、无错误处理

未来方向

  1. 整体框架：同时评估多维度而非孤立指标
  2. 更真实环境：融入 RBAC、动态多用户、领域知识
  3. 自动化可扩展评估：合成数据 + 模拟环境 + Agent-as-Judge
  4. 双层架构：离线框架（CI 回归）+ 在线分类器（捕获新故障）
  5. OpenTelemetry GenAI 标准化：避免厂商锁定，统一追踪语义约定

测试一个 LLM 是检查一个引擎，评估一个 Agent 是测试一辆整车在所有路况下的表现。

多维评估不是可选的，而是 Agent 生产部署的必需品。成熟团队的标配是：一个开源可自托管的可观测平台（如 Langfuse）+ 一套定制化的评估基准（如 SWE-bench 或自建评测集）+ OpenTelemetry 将它们串起来。

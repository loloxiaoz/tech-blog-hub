# Quantifying infrastructure noise in agentic coding evals（量化 Agent 编程评测中的基础设施噪声）

## 核心发现

SWE-bench、Terminal-Bench 这类 agentic 编程基准常被用来比较前沿模型的软件工程能力，榜首之间往往只差几个百分点。这些分数被当作模型相对能力的精确测量，并越来越多地影响部署决策。

但 Anthropic 发现，仅基础设施配置就能产生超过这个差距的差异：在内部实验中，资源最充足与最紧张的配置在 Terminal-Bench 2.0 上相差 6 个百分点（p < 0.01）。

静态基准直接给模型输出打分，运行环境不进入结果；agentic 编程评测不同：模型拿到完整环境，写程序、跑测试、装依赖、多轮迭代。运行时不再是被动容器，而是解题过程的一部分。资源预算与时限不同的两个 agent，做的不是同一张卷子。

评测开发者已开始处理这个问题，例如 Terminal-Bench 2.0 按任务给出推荐的 CPU 与内存。但「规定资源」不等于「一致地执行资源」；而且执行方式本身会改变基准实际测量的东西。

## 问题是怎么发现的

Anthropic 在 Google Kubernetes Engine 上跑 Terminal-Bench 2.0。校准环境时发现分数与官方榜不一致，基础设施错误率也高得意外：多达 6% 的任务因 pod 错误失败，其中多数与模型能否解题无关。

差异来自执行方式。Kubernetes 把每任务资源规格同时当作下限与硬上限：容器保证获得指定资源，一旦超过就立刻被杀。容器运行时用两个独立参数执行资源限制——保证分配（预先预留）与硬性上限（超过即杀）。两者设为同一值时，瞬时峰值没有任何余量：一次短暂的内存波动就能 OOM 杀死本可成功的容器。

Terminal-Bench 榜单用的是另一家更宽松的 sandbox 提供商，允许临时超额分配、不以终止容器为代价，以换取基础设施稳定性。

这引出一个更大的问题：资源配置到底多大程度影响评测分数？

## 六种资源配

固定其他条件（同一 Claude 模型、同一 harness、同一题集），从严格执行每任务规格（1x，同时是地板与天花板）到完全不设上限：

- 基础设施错误率从 5.8% 单调降到 0.5%
- 1x 到 3x：错误率从 5.8% 降到 2.1%（p < 0.001），但成功率在噪声范围内波动（p = 0.40）。1x 下崩溃的任务本来也做不对：agent 探索、撞上资源墙、被抢占，但它从来没有走在正确解法的路上
- 3x 到不设限：错误率再降 1.6 个百分点，成功率却跃升近 4 个百分点
- 不设限相对 1x 总提升 +6 个百分点（p < 0.01）

## 这对测量意味着什么

大约 3x 以内，额外资源主要在修复基础设施可靠性问题，也就是瞬时资源峰值。这不会让评测变简单，只会让它更稳定。

超过 3x 后，额外资源开始实质性地帮助 agent 解决原本解决不了的问题——拉取大依赖、启动昂贵子进程、运行内存密集的测试套件。这说明资源限制会改变评测测量的内容。

严格的限制在无意中奖励非常高效的策略；宽松的限制更宽容，奖励能榨干所有可用资源的 agent。两者都值得测，但混成一个分数、又不说明资源配置，差异与真实世界的泛化性就无法解释。

一个例子：在需要拟合贝叶斯网络的 bn-fit-modify 任务中，有些模型的第一步是安装标准 Python 数据科学栈（pandas、networkx、scikit-learn 及其工具链）。宽松限制下这能跑通；严格限制下，pod 在安装阶段就内存耗尽，agent 还没写一行解法代码。也存在更精简的策略——只用标准库从头实现数学——有些模型默认这么做，有些不会。不同模型有不同的默认路径，而资源配置决定哪条路径恰好能成功。

跨不同 Anthropic 模型复现，效应方向一致，幅度不同。非 Claude 模型上似乎也成立，但尚未严格测试。

在 SWE-bench 上的交叉实验：227 个问题、每个 10 个样本，RAM 提高到基线的 5 倍。分数同样单调上升，但幅度更小，5x 只比 1x 高 1.54 个百分点。SWE-bench 任务资源密集度较低，效应更小是预期之中的，但说明资源分配在那里也并非中性。

## 其他方差来源

资源分配不是唯一的隐藏变量。某些配置下，时间限制也开始起作用。

原则上，评测设置的每个元素都可能影响最终分数：集群健康、硬件规格、并发度、甚至出口带宽。agentic 评测按构造就是端到端系统测试，系统中任何组件都可能成为混杂因素。Anthropic 还观察到通过率随时段波动，可能是因为 API 延迟随流量模式与事故变化。

公开基准通常意在测量纯模型能力，但实践中可能把基础设施的怪癖混进来。有时这是想要的（端到端测试整个栈），但多数时候不是。对公开分享的编码评测，在多个时间、多天运行有助于平均掉噪声。

## 建议

理想情况是在完全相同的硬件条件下运行每个评测——包括运行评测的 scaffold 与推理栈——以确保完全可复现，但这并不总是可行。

考虑到容器运行时实际如何执行资源限制（保证分配 + 独立的硬杀阈值），建议每任务同时规定两个参数，而不是一个钉死的值。单一精确规格会让保证分配等于杀阈值，留下零余量；我们在 1x 记录到的瞬时内存峰值足以让评测失稳。把两个参数分开，可以让容器有足够呼吸空间避免误杀，同时保留硬上限防止分数虚高。

两者之间的带宽应校准到「地板与天花板的分数彼此落在噪声范围内」。例如 Terminal-Bench 2.0 里，3x 上限把基础设施错误率降约三分之二（5.8% 到 2.1%，p < 0.001），同时分数提升温和且落在噪声内（p = 0.40）。这是合理折中：基础设施混杂因素基本被中和，又没有移除有意义的资源压力。

## 为什么在意

这些发现的影响超出评测基础设施。基准分数越来越多被当作决策输入，但这种关注与依赖，并没有总是伴随对「如何运行、如何报告」的同等严谨。

按现状，榜单上 2 个百分点的领先，可能是真实能力差异，也可能只是某次评测跑在更强的硬件上，甚至只是运气更好的时段，或者两者兼有。

对 Anthropic 这样的实验室，含义是：agentic 评测的资源配置应被当作一等实验变量，像 prompt 格式或采样温度一样被记录与控制。

对基准维护者，公开推荐资源规格（Terminal-Bench 2.0 已经在做）能解决很多问题；进一步规定执行方法，则能补上我们发现的缺口。

对任何消费基准结果的人，核心结论是：agentic 评测上的小分差，比报告数字所暗示的精度承载着更大的不确定性。在资源方法标准化之前，低于 3 个百分点的榜单差距值得怀疑，直到评测配置被记录并对齐。几个百分点的领先，可能是真实的能力差距，也可能只是一个更大的虚拟机。

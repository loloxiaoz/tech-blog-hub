Macro Evals for Agentic Systems（Agent 系统的宏观评测）

2026-05-19约 4 分钟EvalAgentMulti-Agent

为什么需要宏观评测

当 agent 系统失败时，问题往往比一次糟糕的回答更大：交接发生得太晚，某个专家 agent 在多次运行中漏掉同一个信号，或者复核流程在错误类型的事件上触发。要改进系统，团队需要看到整个 trace 群体中反复出现的行为。

本文用一个合成的电动车订单流程，演示多 agent 系统的宏观评测工作流。专家 agent 分别处理定价、合规、供应、工厂路由、排程与发布决策，同时市场与运营条件不断变化。

读完之后，你应当能够：

  • 生成或收集大量带 trace 的 agent 运行
  • 对每次完成的运行做低层评测
  • 把每条 trace 转成紧凑文档
  • 在群体中发现反复出现的行为模式
  • 深入一个高影响模式，找到人类下一步最该检查的地方

目标不是为每条 trace 建立完美分类，而是展示 AI 工程团队如何从成千上万个 agent 事件，走到少数技术与非技术干系人都能理解的模式。

为什么需要宏观评测

对简单模型调用，评测可以拿一个输出与 rubric 或参考答案比较。对 agent 系统，还要评估：是否用了正确的工具、是否委派给正确的专家、风险高时是否暂停复核、是否始终扎根于业务上下文。

多 agent 系统更难，因为最终答案只是长流程的最后一个事件。一份发布建议看起来合理，但 trace 可能显示：定价 agent 忽略了激励、供应 agent 漏掉缺货、编排器绕过了必要的复核步骤。

把问题分成两层：

  • 低层评测：给单个 agent、handoff、工具与完成的 run 打分
  • 宏观评测：跨大量低层发现，问哪些问题在重复、集中在哪、先检查工作流的哪一部分

四个面向读者的标签：

  • case_type：生成的业务场景（正常订单、验证阻塞、供应商替换、定价例外）
  • run_outcome：运行如何结束（完成、等待复核、阻塞、失败）
  • eval_finding：低层信号，说明哪里看起来错了或有风险
  • behavior_pattern：跨大量 trace 发现的重复模式

有用心智模型：case_type 是布景，run_outcome 是结局，eval_finding 是局部症状，behavior_pattern 是群体层面的模式。

模拟环境

模拟业务是电动车订单与配置后流程：客户选好车辆配置，公司要决定订单能否原样推进、需要调整、改道、替换，还是暂停复核。

模拟包含真实汽车履约中的约束：

  • 零部件可用性与供应商替换
  • 工厂产能与生产排程
  • 定价例外、促销与激励
  • 关税与带日期的市场信号
  • 地区合规约束
  • 客户澄清与升级路径
  • 高风险或模糊案例的发布复核阈值

agent 群围绕这些业务职责组织：编排器接收订单与当前环境，再分派给验证、供应风险、采购计划、产能平衡、工厂路由、市场情报、定价、合规、客户沟通、发布复核等专家。

用 Promptfoo 做低层评测

成熟的多 agent 系统不应只靠检查最终答案。每个启动的 agent 通常需要自己的评测：这个专家是否用了正确证据、调用了正确工具、遵守政策、在正确时机交接、产出可信的输出？

在真实系统中，有些检查可能在线运行，有些异步运行，有些抽样交人工复核。这里用 Promptfoo 给完成的 trace 打分，问题对应真实系统里的 agent 级评测：

  • 最终决定是否由当前问题推出？
  • 系统是否遵守定价、关税、激励、地区与政策约束？
  • 编排器是否激活了案例隐含的专家？
  • 运行是否回应了带日期的市场信号，而不是把世界当作静态的？
  • 复核或升级是否与风险成比例？

这些检查产出 eval_finding。一个失败的低层评测是局部信号：一条 trace、一个 rubric、一个症状。宏观评测要问的是：这些局部信号在群体规模上会变成什么。

构建分析数据集

把运行包规范成两张分析表：

  • traces_df：每次运行一行，含元数据、结果、发现与文档字段
  • events_df：每个规范化 trace 事件一行（handoff、工具调用、状态事件、模型响应、复核/发现标记）

再构建 trace 文档——它将成为 BERTopic 式聚类建模的对象。

公开的分析路径是：case_type → run_outcome → eval_finding → behavior_pattern。

BERTopic 式发现

发现阶段受 BERTopic 系列方法启发，模块化思路：

  1. 把每条 trace 文档表示为向量
  2. 降维：用 UMAP 之类的 reducer 把向量映射到低维，保留有用的局部邻域
  3. 聚类稠密区域：用 HDBSCAN 之类的密度聚类把邻近点分组，可把离群点标为噪声
  4. 表示每个主题：为每个簇计算能把它与语料其余部分区分开的词项

最后按分诊指标排序模式——一个模式既常见又严重时更重要。

AgentTrace 式诊断

发现告诉你什么在重复，诊断告诉你先查哪里。

对选中的行为模式，重建一张轻量执行图：每个节点是规范化 trace 事件，每条边通过时间顺序、handoff 边界、工具调用层级与邻近执行上下文连接事件。

从一个锚点事件出发，诊断阶段沿图向后走，给上游嫌疑打分：

  • 邻近度：离焦点事件越近分越高
  • 频率：在同一行为模式的多个采样 trace 中反复出现
  • 桥接度：连接执行图不同部分的事件
  • 角色：agent/工具角色与发现的相关性

结论

宏观评测把问题从「这一次运行为什么失败」转为「哪些系统级行为在多次运行中反复失败」。工作流是：

  • 生成或收集大量带 trace 的运行
  • 对每次完成的运行做低层评测
  • 把每条 trace 转成紧凑文档
  • 用 BERTopic 式方法发现重复的行为模式
  • 用 AgentTrace 式方法深入一个高影响模式

同样的闭环适用于真实 agent 系统：保留 trace，用低层评测打分，把打过分数的 trace 变成可比较的文档，聚类文档以发现行为模式，再用最高影响的模式指导人类下一步检查哪里。
